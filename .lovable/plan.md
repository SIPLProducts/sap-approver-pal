# Restore the web application → middleware → SAP login path

## Confirmed cause

The request is reaching `POST /login/Login_API` on the middleware. The 401 is generated by `requireSharedSecret` before any SAP request occurs.

The two sides currently read the header from different places:

- The web app sends `sap_global_secrets.proxy_secret` from the database.
- The middleware compares it with `MIDDLEWARE_SHARED_SECRET` from `middleware/.env`.

Those values are absent or different. This is why the middleware logs `Invalid or missing x-shared-secret`. The `Login_API` row and SAP credentials are not the cause of this specific error.

## Implementation

1. **Use one server-side source for the proxy secret.** Change all web-app-to-middleware calls—including SAP login and normal API invocation—to send `process.env.MIDDLEWARE_SHARED_SECRET`. Stop reading `proxy_secret` from the database for request authentication.
2. **Keep the database for SAP configuration, not middleware authentication.** `middleware_url`, SAP base URL, SAP username and SAP password remain in their existing configuration paths. The shared secret exists only in the app server environment and middleware environment.
3. **Fail clearly before sending.** If `MIDDLEWARE_SHARED_SECRET` is missing on the app server, return a configuration error instead of sending a request without the header. Keep the current safe mismatch message for middleware 401 responses; never log the secret itself.
4. **Make the public middleware endpoints use the same source.** `/api/public/middleware/config` and `/api/public/middleware/log` already validate against `process.env.MIDDLEWARE_SHARED_SECRET`; preserve this so both traffic directions use the same app-server value.
5. **Update deployment templates and instructions.** Require the exact same long random value in:
   - `frontend/.env`: `MIDDLEWARE_SHARED_SECRET=...`
   - `middleware/.env`: `MIDDLEWARE_SHARED_SECRET=...`

   Remove the obsolete instruction to seed `sap_global_secrets.proxy_secret`. Existing database values can remain temporarily but will no longer control middleware authentication.
6. **Retain the self-hosted Node correction.** Produce the Quality build as a plain Node server rather than requiring `wrangler`/`workerd`, so PM2 inherits `frontend/.env` reliably and no `.runtime` install is needed on the server.
7. **Verify the complete flow.** Add focused tests for missing secret, matching secret and 401 mismatch, then validate login reaches the middleware and that the next logged result is the SAP response—not the shared-secret guard.

## Quality server steps after the new build is copied

Set the same secret on both services without printing it in logs, then restart both:

```bash
pm2 restart Qty_App --update-env
pm2 restart Qty_Middleware --update-env
pm2 logs Qty_App --lines 30 --nostream
pm2 logs Qty_Middleware --lines 30 --nostream
```

Expected path:

```text
Browser login
  → Quality app server
  → POST http://127.0.0.1:3002/login/Login_API
     x-shared-secret: <app server environment value>
  → middleware validates the same environment value
  → middleware calls SAP Login_API
  → app creates the authenticated session
```

No secret value will be committed, returned to the browser, or written to logs.
