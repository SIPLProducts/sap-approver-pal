# Fix: the app server can't see its Supabase variables

## What the error actually means

`Missing Supabase environment variable(s): SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY` comes from the privileged database client inside the login server function. It is not a Lovable Cloud connection problem — on the Quality server it means the local worker runtime that serves port 8080 is starting with an empty environment.

The launcher (`dist/start.mjs`) loads `.env.runtime` into the Node process, and the log line `[start] loaded env from .env.runtime` confirms that part works. But the app itself does not run in that Node process — it runs inside the local worker sandbox that the launcher starts. Variables in the parent process are **not** inherited as bindings by that sandbox, so `process.env['SUPABASE_URL']` is undefined inside the app. That is the whole bug.

## The fix

1. Change the launcher generated by `scripts/collect-dist.mjs` so it passes each server variable to the runtime explicitly as a binding rather than relying on process inheritance. Covered: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_PROJECT_ID`, `MIDDLEWARE_URL`, `MIDDLEWARE_SHARED_SECRET`, plus any other non-`VITE_` key present in `.env.runtime`.
2. Add a startup guard: if `SUPABASE_URL` or `SUPABASE_SERVICE_ROLE_KEY` is blank, the launcher exits with a one-line message naming the missing keys instead of booting a server that fails on every login. Names only — never values.
3. Add a warning when `SUPABASE_SERVICE_ROLE_KEY` is not a service-role key. The value currently in your `.env` decodes to `"role":"anon"`, which cannot create the backend session even once the binding reaches the app. Replace it with the real one:

```bash
grep -E '^SERVICE_ROLE_KEY=' /data/webapplication/resl_approval/Quality/supabase/.env
```

4. Print a one-line startup summary listing which expected keys were found (names only), so the next restart tells you immediately whether the environment is complete.

Also still open from the previous step: the middleware rejected `x-shared-secret: 123456`, so `MIDDLEWARE_SHARED_SECRET` in `frontend/.env` and `proxy_secret` in the `sap_global_secrets` row must both match `middleware/.env`. The login function sends the value from the database row, not from the env file.

## Database rows

`Login_API` in `sap_api_configs` is confirmed present and active. Two rows keyed `default` are still required, and I'll ship them as one re-runnable seed migration:

- `sap_global_settings`: `middleware_url` = `http://127.0.0.1:3002`, SAP base URL, SAP username, `connection_mode` = `via_proxy`, `deployment_mode` = `self_hosted`.
- `sap_global_secrets`: `proxy_secret` = the real middleware secret, `sap_password` for SAP.

## After I make the change

Locally: `npm run build`, then copy `dist/` to the server, then:

```bash
cd /data/webapplication/resl_approval/Quality/frontend/dist
pm2 restart Qty_App --update-env
pm2 logs Qty_App --lines 30 --nostream
```

Expect the startup summary listing the found keys and `serving app server on http://0.0.0.0:8080`, with no "Missing Supabase environment variable(s)" when you sign in. The repeated `Unable to fetch the Request.cf object` / `TimeoutError` lines are harmless offline noise and do not block the server.

Rotate the keys and the shared secret pasted into chat once login works.
